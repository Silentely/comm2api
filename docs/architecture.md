## 全局架构总览

## 反检测与硬件指纹伪装

Command Code 官方 CLI 在运行时会上报设备特征以做风控和会话识别。`comm2api` 通过对官方 CLI（`command-code@1.88.0`）的网络流量与源码逆向分析，实现了 1:1 的防检测对齐：

### 1. 确定性设备指纹 (Deterministic Fingerprint)
- **非随机生成**：每次重启或不同实例中，同一个 API Key 必须上报完全一致的设备硬件特征。
- **派生算法**：代理基于 `apiKey` 与可选的 `CC_FINGERPRINT_SALT` 确定性派生出：
  - Windows `MachineGuid` 格式 UUID；
  - 真实格式的 MAC 地址；
  - 符合规范的主机名（如 `DESKTOP-XXXXXX`）。
- **初始化上报**：Key 首次发起请求前，先向 `/alpha/fingerprint/record` 发送指纹记录。

### 2. 单一真源硬件档案 (DEVICE_PROFILE)
上游风控会比对多个字段的自洽性。代理内置了一份标准的 `DEVICE_PROFILE`（固定伪装为 Windows x64 平台）：
- 设备指纹、`config.environment`、`config.workingDir`、`x-project-slug` 以及 lifecycle 的 `os` 全面同源；
- 绝不向官方泄露部署服务器真实的 Linux 平台、真实主机名或当前目录。

### 3. 生命周期事件与会话标识
- Key 初始化时并行发送 `POST /alpha/lifecycle-events`（上报 `cli_session_exists` 事件）。
- 会话 ID（Session ID）根据请求内容（Key + Model + System + 首段文本）哈希确定性生成，保持 Prompt 缓存断点最大化命中。

### 4. 协议版本号漂移告警
- 请求头 `x-command-code-version` 真实回显代理所对齐的协议版本号（`1.88.0`）。
- 当上游 npm 发布更高版本时，代理仅在日志中输出版本漂移告警（drift warning），绝不盲目假冒新版本号，防止协议格式不兼容引起封禁。

### 5. 字符编码安全（孤立代理项清洗）
客户端在截断长文本或 Emoji 时，可能会产生孤立的 UTF-16 半代理项（Lone Surrogates）。标准 `JSON.stringify` 会将其序列化为 `\ud83d`，导致严格的上游解析器报 400 错误。代理在出网序列化点使用统一的 Replacer 净化孤立项，成对的合法 Emoji 则原样完整保留。

## 上游 Command Code 通信协议细节

### 1. 9 键信封规范
所有发往 `/alpha/generate` 的负载均被包装为符合官方 CLI 规范的 9 键对象：
```json
{
  "config": {
    "workingDir": "C:\\Users\\dev\\projects\\app",
    "date": "2026-11-20",
    "environment": "win32",
    "structure": [],
    "isGitRepo": false
  },
  "memory": null,
  "taste": null,
  "skills": null,
  "permissionMode": "standard",
  "params": {
    "model": "deepseek/deepseek-v4-flash",
    "messages": [...],
    "max_tokens": 64000,
    "stream": true,
    "reasoning_effort": "max"
  }
}
```

### 2. 空白 System 占位符
当客户端请求中没有传递任何 system prompt 时，官方上游会默认自动注入一段长达约 7,500 token 的默认指令。代理默认开启 `emptySystemPlaceholder=true`，主动发送单空格占位，有效阻断这 7.5K 提示词的隐式注入，大幅降低响应延迟与上下文消耗。

### 3. 历史思考占位符补齐
当客户端回放历史会话但 assistant 消息中缺少 reasoning 内容时，代理会自动补全占位符并保留当前轮次的 `reasoning_effort`，确保思考模型对话链路的连续性。

## 高可用与网络容灾机制

### 首字未吐前的无缝重试
在网络高峰期，上游偶尔会在握手或生成初期重置连接（`terminated` / `ECONNRESET` / FIN 截断）。
- **重试前置判据**：若代理**尚未向下游客户端写出任何 HTTP Header 或字节**，则此次故障对客户端而言是完全不可见的。
- **自动消化抖动**：代理会立即在内部执行指数退避重试（默认最多 2 次，共 3 次尝试），彻底吸收上游网络瞬断，客户端仅能感知到一次正常的 200 响应。
- **安全边界**：一旦已经向下游写出过 Header 或 SSE Chunk，则立即锁定，绝不再重试，防止客户端读到重复生成内容。

### 读空闲看门狗与长思考保护
- 针对流式请求设置 `CC_STREAM_IDLE_MS`（默认 180s），针对非流式请求设置 `CC_NONSTREAM_IDLE_MS`（默认 90s）。
- **计时语义**：看门狗监控的是两次数据分块之间的等待时间，每收到一个 Chunk 即清零重置，**并非限制整个请求的总时长**。大模型长达数十分钟的生成过程完全不受影响。
- 超时后主动返回携带 `Retry-After` 的 429 错误，通知下游客户端 SDK 智能重发。

### 输出上限自适应学习
不同模型在上游各具不同的 `max_tokens` 物理限制（例如部分模型上限为 128,000）。当客户端传入过大参数导致上游报 400 并提示具体上限时：
- 代理会自动解析错误文本中的真实数字（如 `128000`）；
- 将其记入进程级自适应缓存表；
- 自动调小参数并仅重发该请求一次；
- 后续同类请求在构造阶段直接预先夹持至安全值，避免每个请求都白白消耗一次失败往返。

### 流控背压与内存防膨胀
- 基于 Node.js Socket `drain` 事件实现端到端背压传输。下游慢速读取时，上游拉取自动停顿，防止上百兆数据无底线积压在 Node 堆内存中。
- 请求体前置校验：超大请求在解析阶段由 `CC_MAX_BODY_MB`（默认 100MB）直接阻断并返回 413，释放 TCP 缓冲区。

## 终态感知访问日志

流式响应在发出 `200 OK` 头部后，后续无论正常结束还是看门狗超时，HTTP 状态码均无法反映真实结果。因此 `comm2api` 为每个请求记录一行结构化终态日志：

```json
{
  "method": "POST",
  "path": "v1/chat/completions",
  "status": 200,
  "durationMs": 4215,
  "streaming": true,
  "model": "deepseek/deepseek-v4-flash",
  "outcome": "ok",
  "bytesOut": 3280
}
```

### outcome 枚举取值定义

| outcome | 含义说明 |
|---|---|
| `ok` | 请求完整传输且正常收尾 |
| `stream_idle_timeout` | 上游在生成中途静默超时（卡在读空闲） |
| `stream_incomplete` | 上游连接关闭但未发送 finish 结束事件 |
| `zero_output` | 上游正常关闭但未输出任何有效 token（触发防空转机制） |
| `upstream_error` | 上游返回了明确的错误事件或异常状态码 |
| `client_disconnected` | 客户端主动挂断或网络断开 |
| `socket_closed` | 传输异常中断，连接被底层操作系统切断 |
